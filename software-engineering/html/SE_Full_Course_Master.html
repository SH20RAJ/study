Topic 4 – 10: Software Development Process Models

Process Model Core Lifecycle Mechanism & Characteristics Ideal Project Suitability
1. Waterfall Model Strict linear sequential phases (Requirements $\rightarrow$ Design $\rightarrow$ Code $\rightarrow$ Test $\rightarrow$ Deploy). Each phase produces sign-off deliverables before the next begins. Well-understood, stable requirements with mature technology stacks (e.g., Space flight software, banking backends).
2. Prototyping Builds an early disposable mock-up interface to elicit feedback, refine ambiguous user requirements, and discard/re-engineer. High user interaction systems where clients have unclear or fuzzy initial requirements.
3. Spiral Model (Boehm) Risk-driven iterative model structured in 4 quadrants: (1) Objective Determination, (2) Risk Analysis, (3) Engineering, (4) Customer Evaluation. Large-scale, expensive, mission-critical, high-risk enterprise projects.
4. RAD Model Rapid Application Development ($60\text{–}90$ days) utilizing component-based construction, GUI builders, and automated code generators. Well-modularized information systems with short delivery deadlines and high component reuse.
5. Incremental Model System is decomposed into modular release increments. Increment 1 delivers core functionality; subsequent releases add peripheral features. Projects requiring early partial operational software release to capture market share.
6. Agile (Scrum / XP) Iterative 2–4 week Sprints emphasizing working software over documentation, customer collaboration, and adaptive response to changing requirements. Dynamic web/mobile products with volatile, continuously evolving market requirements.
🧠 Memory Hook: Process Model Selection Strategy
• Stable requirements $\rightarrow$ Waterfall
• Unclear user requirements $\rightarrow$ Prototyping
• High financial/technical risk $\rightarrow$ Spiral
• Rapid component delivery $\rightarrow$ RAD / Incremental
• Changing, dynamic requirements $\rightarrow$ Agile

Topic 11 – 14: Project Planning, Scheduling & Risk Management

The 5-Stage Risk Management Cycle (I-A-P-M-M)
  1. Risk Identification: Identify project, product, and business risks (e.g., staff turnover, scope creep).
  2. Risk Analysis (Estimation): Quantify Risk Probability ($P$) and Risk Impact / Severity ($I$). $\text{Risk Exposure } (RE) = P \times I$.
  3. Risk Prioritization: Rank risks in a Risk Matrix to focus engineering resources on top hazards.
  4. Risk Mitigation (RMMM Plan): Develop Risk Mitigation, Monitoring, and Management strategies to minimize impact.
  5. Risk Monitoring: Continuously track risk indicators throughout the project lifecycle.

1. Requirement Flexibility: Waterfall is rigid; Prototyping clarifies fuzzy needs; Spiral adapts per cycle; Agile welcomes changes at any stage.
2. Risk Management: Spiral explicitly incorporates formal Risk Analysis in every cycle; Waterfall and Prototyping have zero built-in risk analysis; Agile manages risk via short sprint iterations.

4. Delivery Schedule: Waterfall delivers product only at the very end; Incremental/Agile delivers functional software increments every few weeks.
5. Cost & Documentation: Waterfall is documentation-heavy; Spiral is expensive due to risk experts; Agile prioritizes working software over extensive documentation.

Topic 15 – 18: Functional vs. Non-Functional & User vs. System Requirements

Requirement Class Formal Definition & Scope Concrete Illustrative Example
1. Functional Specifies WHAT services, computations, and transformations the software must perform in response to specific inputs. "The banking system shall transfer funds between accounts and send SMS confirmation within 5 seconds."
2. Non-Functional Specifies HOW WELL the system operates, defining constraints on quality attributes: Performance, Security, Availability, Usability. "The system shall maintain $99.99\%$ annual availability and encrypt database records using AES-256."
3. User Requirements High-level natural language statements + informal diagrams intended for non-technical clients and executive sponsors. "Patients should be able to book doctor consultations online."
4. System Requirements Structured, unambiguous technical contracts detailing software services, inputs, outputs, exceptions, and DB schemas for developers. "The API endpoint `POST /api/v1/appointments` shall validate doctor availability locks via Redis mutexes."

Topic 19 – 21: The SRS Document & IEEE 830 Standard

🧠 The 9 Characteristics of a High-Quality SRS (C-U-C-C-V-F-T-P-M)
  1. Correct: Every requirement accurately reflects actual customer needs.
  2. Unambiguous: Every requirement has exactly ONE possible interpretation by developers and testers.
  3. Complete: All critical functional capabilities, responses to errors, and constraints are specified.
  4. Consistent: Zero contradictions between individual requirements or interface definitions.
  5. Verifiable (Testable): A finite, cost-effective test case can prove whether the software satisfies the requirement.
  6. Feasible: The requirement is achievable within project budget, timeline, and technology constraints.
  7. Traceable: Each requirement has a unique identifier linked backward to user needs and forward to code/tests.
  8. Prioritized: Requirements are ranked by business importance (Essential, Desirable, Optional).
  9. Modifiable: Organized with a clear table of contents and cross-references for easy updates.

Topic 27 – 30: Fundamental Software Design Concepts

Design Concept Engineering Principle & Definition Key Benefit

2. ModularityDecomposing software into discrete, independently testable, naming-addressable modules.Enables parallel team development and isolated debugging.

Topic 33 & 34: Cohesion vs. Coupling (The Cornerstone of Modular Design)

Cohesion Level (Internal Focus) Operating Semantics Quality Rating
1. Functional CohesionEvery instruction in the module contributes to executing exactly ONE single mathematical/business function (e.g., `calculate_tax()`).⭐⭐⭐⭐⭐ BEST
2. Sequential CohesionOutput data from one operation serves as direct input to the next operation in the module.⭐⭐⭐⭐ Very Good
3. Communicational CohesionFunctions operate on the exact same input data structure (e.g., `print_student_record()` and `save_student_record()`).⭐⭐⭐ Good
4. Procedural / TemporalFunctions executed in a sequence or executed at the same time (e.g., `startup_initialization()`).⭐⭐ Moderate
5. Coincidental CohesionArbitrary unrelated tasks grouped together in a `utils.py` file with no logical relationship.⭐ WORST
Coupling Level (Inter-Dependency) Operating Semantics Quality Rating
1. Data CouplingModules communicate strictly by passing necessary simple primitive data parameters ($x, y$).⭐⭐⭐⭐⭐ BEST
2. Stamp CouplingModules pass entire complex data structures when only a single field is actually needed.⭐⭐⭐⭐ Good
3. Control CouplingOne module passes a control flag (`bool is_admin`) that dictates the internal execution path of another.⭐⭐ Moderate
4. Common CouplingMultiple modules read and write to shared global variables.⭐ Poor
5. Content CouplingOne module directly accesses, modifies, or branches into the internal memory/code of another module.💥 WORST
🧠 Golden Rule of Software Design
HIGH COHESION (Functional) + LOW COUPLING (Data) = Publication-Grade Software Architecture!

🧠 M3 Active Recall & Exam Questions

Q1. Differentiate between `<>` and `<>` relationships in UML Use Case Diagrams with examples. (8 Marks)
- `<>` Relationship: Represents mandatory common functionality unconditionally shared across multiple use cases. The base use case cannot execute without invoking the included use case.
Example: `PlaceOrder` $\xrightarrow{<>}$ `AuthenticateUser`.
- `<>` Relationship: Represents optional, conditional behavior that executes only when a specific extension point condition is met at runtime.
Example: `CalculateTotal` $\xleftarrow{<>}$ `ApplyDiscountCoupon` (executed only if the customer possesses a valid coupon code).

Topic 50: Basis Path Testing & McCabe's Cyclomatic Complexity

McCabe's Cyclomatic Complexity $V(G)$ Formulations (McCabe, 1976): 1. From Edges ($E$) and Nodes ($N$): $\mathbf{V(G) = E - N + 2}$ 2. From Predicate / Decision Nodes ($P$): $\mathbf{V(G) = P + 1}$ 3. From Enclosed Regions ($R$): $\mathbf{V(G) = R}$ Significance: $V(G)$ defines the exact number of linearly independent execution paths required to achieve $100\%$ branch coverage!
🏛️ Step-by-Step Solved Problem: Cyclomatic Complexity & Independent Paths
int find_max(int a, int b, int c) {
    int max = a;            // Node 1
    if (b > max)            // Node 2 (Predicate)
        max = b;            // Node 3
    if (c > max)            // Node 4 (Predicate)
        max = c;            // Node 5
    return max;             // Node 6
}

Graph Analysis: Nodes $N = 6$, Edges $E = 7$, Predicates $P = 2$ (Nodes 2 and 4).

$$V(G) = E - N + 2 = 7 - 6 + 2 = \mathbf{3} \quad (\text{or } P + 1 = 2 + 1 = \mathbf{3})$$

Set of 3 Linearly Independent Paths:

  • Path 1: $1 \rightarrow 2 \rightarrow 4 \rightarrow 6$ (Test: $a=10, b=5, c=2$)
  • Path 2: $1 \rightarrow 2 \rightarrow 3 \rightarrow 4 \rightarrow 6$ (Test: $a=5, b=10, c=2$)
  • Path 3: $1 \rightarrow 2 \rightarrow 4 \rightarrow 5 \rightarrow 6$ (Test: $a=5, b=2, c=10$)

🧠 M4 Active Recall & Exam Questions

Q1. Explain Top-Down vs. Bottom-Up Integration Testing. Define Stubs and Drivers with diagrams. (10 Marks)
- Top-Down Integration: Modules are integrated from top to bottom of the control hierarchy. Subordinate modules not yet developed are simulated using Stubs (dummy subroutines called by the tested module).
- Bottom-Up Integration: Low-level worker modules are tested first. Superordinate modules not yet developed are simulated using Drivers (test harnesses that invoke the module and display results).
- Sandwich (Hybrid) Integration: Combines top-down for top layers and bottom-up for low-level utility libraries, minimizing stub/driver development overhead.

Topic 61: Boehm's COCOMO Model (Constructive Cost Model)

Basic COCOMO Equations (Barry Boehm, 1981): $$\text{Effort } (E) = a \cdot (\text{KLOC})^b \quad [\text{Person-Months (PM)}]$$ $$\text{Development Time } (T_{\text{dev}}) = c \cdot (E)^d \quad [\text{Months}]$$ $$\text{Average Staffing Size } (SS) = \frac{E}{T_{\text{dev}}} \quad [\text{Persons}], \quad \text{Productivity} = \frac{\text{KLOC}}{E} \quad [\text{KLOC/PM}]$$
Project Mode Team & Environment Characteristics Effort ($a, b$) Time ($c, d$)
1. OrganicSmall, experienced teams working with flexible requirements in familiar in-house environment.$E = 2.4(\text{KLOC})^{1.05}$$T_{\text{dev}} = 2.5(E)^{0.38}$
2. Semi-DetachedMedium teams with mixed experience levels working under intermediate constraints.$E = 3.0(\text{KLOC})^{1.12}$$T_{\text{dev}} = 2.5(E)^{0.35}$
3. EmbeddedExtremely tight, rigid hardware/software interface constraints (e.g., flight control, medical systems).$E = 3.6(\text{KLOC})^{1.20}$$T_{\text{dev}} = 2.5(E)^{0.32}$

Topic 62: Function Point (FP) Analysis (Albrecht, 1979)

Function Point Mathematical Formulations: $$\mathbf{\text{FP} = \text{UFP} \times \text{VAF} = \text{UFP} \times \left[ 0.65 + 0.01 \times \sum_{i=1}^{14} C_i \right]}$$ Where $\text{UFP}$ is Unadjusted Function Points, and $\sum C_i$ is the sum of 14 General System Characteristics (TDI: 0 to 70).

Topic 66 – 68: SCM & The 4 Types of Software Maintenance (CAP-P)

🧠 Memory Hook: The 4 Maintenance Types (CAP-P)
  • 1. Corrective Maintenance (20%): Reactive fixing of residual bugs discovered in production.
  • 2. Adaptive Maintenance (25%): Modifying software to operate in new environments (OS upgrade, cloud migration).
  • 3. Perfective Maintenance (50% — Largest): Enhancing existing functionality, performance, and user convenience.
  • 4. Preventive Maintenance (5%): Refactoring code to enhance maintainability and prevent future software decay.

🧠 M5 Active Recall & Exam Questions

Q1. A 30 KLOC software is developed in Organic mode. Calculate Effort, Development Time, Staff Size, and Productivity using Basic COCOMO. (8 Marks)
Given: $\text{Size} = 30 \text{ KLOC}$, Mode: Organic ($a=2.4, b=1.05, c=2.5, d=0.38$).
1. $\text{Effort } E = 2.4 \times (30)^{1.05} = 2.4 \times 35.64 \approx \mathbf{85.54 \text{ Person-Months}}$.
2. $\text{Development Time } T_{\text{dev}} = 2.5 \times (85.54)^{0.38} = 2.5 \times 5.43 \approx \mathbf{13.58 \text{ Months}}$.
3. $\text{Average Staff Size } SS = \frac{E}{T_{\text{dev}}} = \frac{85.54}{13.58} \approx \mathbf{6.3 \text{ Persons}}$.
4. $\text{Productivity} = \frac{30}{85.54} \approx \mathbf{0.351 \text{ KLOC/PM}} \ (\mathbf{351 \text{ LOC/PM}})$.
