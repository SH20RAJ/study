Topic 1 – 4: Traditional Prescriptive Process Models

A Software Process Model is an abstract representation of the lifecycle activities, actions, tasks, milestones, and work products required to build high-quality software.

Process Model Core Operational Philosophy Ideal Project Characteristics
1. Classical Waterfall Strictly linear sequential progression. Downstream phases only begin once upstream deliverables are frozen. Requirements are 100% clear, stable, and well-understood; safety-critical systems with rigid standards.
2. V-Model Pairs each development phase on the left descending arm with its corresponding testing verification phase on the right ascending arm. High-reliability systems where test plan generation occurs early in parallel with requirements.
3. Prototyping Builds a quick mock-up interface to elicit, clarify, and validate ambiguous user requirements. High user interaction systems where clients cannot articulate exact requirements upfront.
4. Boehm's Spiral Model Risk-driven iterative model combining iterative prototyping with Waterfall systematic control. Evaluates risk in 4 quadrants per cycle. Large-scale, expensive, high-risk enterprise systems with emerging requirements.

Topic 6: Boehm's Spiral Model (4 Quadrants of Iteration)

The 4 Quadrants of the Spiral Model Cycle
  1. Quadrant 1: Determine Objectives, Alternatives & Constraints: Identify specific phase goals, alternative architectural options, and operational constraints (cost, schedule).
  2. Quadrant 2: Identify & Resolve Risks (Risk Analysis): Detailed risk evaluation; create simulations, benchmarks, or prototypes to mitigate technical and project risks.
  3. Quadrant 3: Develop & Verify Next-Level Product: Engineering design, coding, and verification testing of the release increment.
  4. Quadrant 4: Review & Plan Next Phase: Customer evaluation of the increment, review progress, and plan the next spiral loop.

Q1. Compare the Waterfall Model and the Spiral Model across 4 engineering parameters. (8 Marks)
1. Risk Management: Waterfall has zero explicit risk management mechanisms; Spiral is fundamentally driven by continuous risk analysis in every cycle.
2. Handling Changing Requirements: Waterfall resists changes after requirements freeze; Spiral accommodates evolving requirements in subsequent spiral loops.
3. Customer Involvement: In Waterfall, customer interaction happens only at the beginning (requirements) and end (delivery); in Spiral, customer evaluates prototypes after every loop.
4. Project Cost & Complexity: Waterfall is suitable for small, simple projects; Spiral is designed for large-scale, complex, mission-critical systems.

Topic 2 – 4: Requirements Engineering & The IEEE 830 SRS Standard

A Software Requirements Specification (SRS) is a formal contract between the client and the development organization describing the complete functional behavior and operational constraints of the system.

SRS Section (IEEE 830) Mandatory Content & Description Key Invariants & Purpose
1. Introduction Purpose of the system, project scope, definitions, acronyms, and references. Sets project boundary; prevents scope creep.
2. Overall Description Product perspective, user classes, operating environment, design constraints, assumptions. Provides high-level context without dictating low-level implementation details.
3. Specific Requirements Detailed Functional Requirements, External Interface Requirements (UI, HW, SW), Non-Functional Requirements (Performance, Security, Reliability). Must be 100% Unambiguous, Complete, Consistent, Verifiable (Testable), and Traceable.

Topic 6 – 8: Data Flow Diagrams (DFD) & Balancing Rules

DFD Symbol DeMarco & Yourdon Gane & Sarson Functional Meaning

Data FlowDirected ArrowDirected ArrowPipeline along which packets of data travel.

DFD Balancing & Consistency Invariants
  • Conservation of Data: A process cannot output data that was not present in or computable from its input data.
  • Black Hole Error: A process that has inputs but zero outputs.
  • Miracle Error: A process that generates outputs with zero inputs.
  • Gray Hole Error: A process where outputs require data not supplied by its inputs.
  • Level Balancing: All input data flows and output data flows entering/leaving a parent process bubble in DFD Level $N$ must exactly match the external data flows in its child Level $N+1$ diagram.

🏛️ Top BIT Mesra Exam Questions & Answers (Module II)

Q1. Differentiate between `<>` and `<>` relationships in Use Case Diagrams with examples. (8 Marks)
1. `<>` (Mandatory Shared Behavior): The base use case unconditionally and explicitly invokes the included use case every single time it executes. Used to factor out common repeated subroutines.
Example: `Withdraw Cash` $\xrightarrow{<>}$ `Authenticate User PIN`.
2. `<>` (Optional / Conditional Behavior): The extending use case executes only if a specific extension condition holds true at designated extension points in the base use case. The base use case is completely functional on its own without knowing about the extension.
Example: `Calculate Premium` $\xleftarrow{<>}$ `Apply Senior Citizen Discount` (only if $\text{age} \ge 60$).

Topic 3 & 4: Modularity (Cohesion vs. Coupling)

The primary objective of software modularization is to achieve High Cohesion (Single Responsibility within a module) and Low Coupling (Minimal Interdependence between modules).

Cohesion Type (High to Low) Definition & Internal Binding Characteristics Quality Rating
1. FunctionalAll elements of a module contribute to executing a single, well-defined mathematical task (e.g., `computeSquareRoot()`).⭐⭐⭐⭐⭐ (Ideal)
2. SequentialThe output data of one element serves as the direct input to the next element inside the module (e.g., `readRecordAndFormat()`).⭐⭐⭐⭐ (High)
3. CommunicationalElements operate on the exact same input data structure or produce the same output structure (e.g., `updateAndPrintCustomerReport()`).⭐⭐⭐ (Medium)
4. ProceduralElements are grouped because they execute in a specific sequential algorithmic order (e.g., `readInputsThenValidate()`).⭐⭐ (Fair)
5. TemporalElements are grouped simply because they are executed at the same time (e.g., system `startupInit()` or `shutdown()`).⭐ (Poor)
6. LogicalElements perform logically similar tasks selected by a control flag (e.g., a single function with a switch case for all math operations).⭐ (Poor)
7. CoincidentalElements have zero meaningful relationship; grouped purely by accident or arbitrary convenience.❌ (Worst)
Coupling Type (Low to High) Definition & Inter-Module Communication Quality Rating
1. Data CouplingModules communicate strictly by passing elementary primitive data parameters (e.g., `int`, `float`).⭐⭐⭐⭐⭐ (Ideal)
2. Stamp CouplingModules pass complex composite data structures (e.g., entire `CustomerRecord`), even when the callee only needs a few fields.⭐⭐⭐⭐ (Good)
3. Control CouplingOne module passes a control flag (`bool`, `enum`) that dictates the internal execution flow of the other module.⭐⭐ (Poor)
4. Common CouplingMultiple modules share and mutate global variables or shared global memory blocks.⭐ (Very Poor)
5. Content CouplingOne module directly accesses, modifies, or branches into the internal private code/memory of another module (e.g., modifying private memory).❌ (Worst)

🏛️ Top BIT Mesra Exam Questions & Answers (Module III)

Q1. Explain the SOLID design principles in Object-Oriented Software Engineering. (10 Marks)
- S (Single Responsibility Principle): A class should have only one reason to change, encapsulating a single responsibility.
- O (Open/Closed Principle): Software entities should be open for extension, but closed for modification (achieved via interfaces and polymorphism).
- L (Liskov Substitution Principle): Subtypes must be substitutable for their base types without altering program correctness.
- I (Interface Segregation Principle): Clients should not be forced to depend on interfaces they do not use (prefer small, client-specific interfaces over fat general ones).
- D (Dependency Inversion Principle): High-level modules should not depend on low-level modules; both should depend on abstractions.

Basic COCOMO Effort & Schedule Equations: $$\text{Effort } (E) = a \times (\text{KLOC})^b \quad \text{Person-Months (PM)}$$ $$\text{Development Time } (T_{\text{dev}}) = c \times (E)^d \quad \text{Months}$$ $$\text{Average Staffing } (\text{Staff}) = \frac{E}{T_{\text{dev}}} \quad \text{Persons}$$
Project Mode Characteristics $a$ $b$ $c$ $d$
1. Organic Small teams, familiar in-house domain, relaxed constraints. 2.4 1.05 2.5 0.38
2. Semi-Detached Medium teams, mixed experience levels, medium constraints. 3.0 1.12 2.5 0.35

🏛️ Step-by-Step Solved Problem: Basic COCOMO Estimation for a 30 KLOC Semi-Detached Project
  1. Step 1: Compute Effort ($E$): $$E = 3.0 \times (30)^{1.12} = 3.0 \times 44.91 = \mathbf{134.73} \text{ Person-Months}$$
  2. Step 2: Compute Development Time ($T_{\text{dev}}$): $$T_{\text{dev}} = 2.5 \times (134.73)^{0.35} = 2.5 \times 5.54 = \mathbf{13.85} \text{ Months}$$
  3. Step 3: Compute Average Staffing Size: $$\text{Staff} = \frac{E}{T_{\text{dev}}} = \frac{134.73}{13.85} \approx \mathbf{9.7} \implies \mathbf{10} \text{ Engineers}$$

Q1. State the components of an RMMM (Risk Mitigation, Monitoring, and Management) plan. (8 Marks)
1. Risk Mitigation (Proactive Prevention): Developing actionable strategy to reduce the probability of risk occurrence.
Example: High developer turnover risk $\rightarrow$ cross-training team members and establishing thorough documentation standards.
2. Risk Monitoring (Tracking): Continuously observing warning indicators to detect when a risk is transitioning from potential threat to reality.

3. Risk Management (Contingency Action): Executing contingency plans when mitigation fails and the risk actually occurs.
Example: Activating backup external contractors if a key developer departs.

Topic 2: Black-Box (Functional) Testing Techniques

Testing Method Test Case Derivation Principle Example for Input Range $[1, 100]$
1. Equivalence Class Partitioning (ECP) Divides input domain into valid and invalid equivalence classes. One test case is selected to represent each class. • Valid Class: $[1, 100]$ (e.g., $50$)
• Invalid Class 1: $< 1$ (e.g., $-5$)
• Invalid Class 2: $> 100$ (e.g., $150$)
2. Boundary Value Analysis (BVA) Selects test cases at the extreme boundaries and just inside/outside boundaries ($Min, Min+, Nom, Max-, Max$). Test values: $1$ (Min), $2$ (Min+), $50$ (Nom), $99$ (Max-), $100$ (Max), plus invalid boundaries $0$ and $101$.

Topic 3 & 4: White-Box Testing & McCabe's Cyclomatic Complexity

McCabe's Cyclomatic Complexity ($V(G)$) Formulas: Let $G$ be the Control Flow Graph of a program: 1. Formula 1 (Edges & Nodes): $$V(G) = E - N + 2P$$ Where $E$ is number of flow graph edges, $N$ is number of nodes, and $P$ is number of connected components ($P=1$ for single programs). 2. Formula 2 (Predicate Nodes): $$V(G) = P + 1$$ Where $P$ is the number of binary decision/conditional predicate nodes (`if`, `while`, `for`). 3. Formula 3 (Enclosed Regions): $$V(G) = \text{Number of Enclosed Planar Regions} + 1 \text{ (Outer Region)}$$
🏛️ Step-by-Step Solved Problem: Cyclomatic Complexity & Basis Paths Calculation

Code Snippet:

1: if (a > 10) {
2:     if (b < 20)
3:         x = 1;
4:     else
5:         x = 2;
6: } else {
7:     x = 3;
8: }
9: return x;
  1. Predicate Nodes ($P$): Two conditional tests (Node 1: `a > 10`, Node 2: `b < 20`).
  2. Cyclomatic Complexity: $V(G) = P + 1 = 2 + 1 = \mathbf{3}$.
  3. 3 Linearly Independent Basis Paths: - Path 1: $1 \rightarrow 6 \rightarrow 7 \rightarrow 9$ (Condition 1 is False). - Path 2: $1 \rightarrow 2 \rightarrow 3 \rightarrow 9$ (Condition 1 is True, Condition 2 is True). - Path 3: $1 \rightarrow 2 \rightarrow 5 \rightarrow 9$ (Condition 1 is True, Condition 2 is False).

Topic 9: Mutation Testing & Quality Evaluation

Mutation Score ($\text{MS}$) Formula: $$\text{Mutation Score } (\text{MS}) = \frac{D}{T - E} \times 100\%$$ Where $T$ is total generated mutants, $D$ is number of killed (detected) mutants, and $E$ is number of equivalent mutants (mutants that have identical functional behavior to original program).

🏛️ Top BIT Mesra Exam Questions & Answers (Module V)

Q1. Compare Stubs and Drivers in Integration Testing with diagrams. (8 Marks)
- Driver: A dummy calling program written to invoke and pass test data to the module under test. Used extensively in Bottom-Up Integration Testing where high-level parent control modules have not yet been developed.
- Stub: A dummy called subroutine that simulates the interface and returns dummy values for sub-modules invoked by the module under test. Used extensively in Top-Down Integration Testing where low-level worker modules have not yet been developed.
